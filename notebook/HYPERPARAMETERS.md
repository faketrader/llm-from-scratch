# 数值与超参数阅读手册

本手册用于区分 Notebook 中不同类型的数值。并非所有数字都是可调参数，也不存在可以脱离任务直接复用的配置答案。合理的分析顺序是先识别数值类型，再评估取值依据及调整影响。

各章在相应代码或配置首次定义处解释实际使用的关键数值；本手册负责给出跨章节通用的决策方法。局部注释用于理解当前实现，本手册用于比较选择方法，两者不能相互替代。

常用记号约定如下：`3e-4` 表示 $3\times10^{-4}=0.0003$；`step` 在训练配置中通常指一次 optimizer update，但部分日志也以 step 表示 micro-batch，具体含义以章节定义为准；`epoch` 表示完整遍历一次有限训练集；样本 batch 与 Token batch 采用不同口径；GB 使用十进制字节，GiB 使用二进制字节。百分位延迟 `P95` 表示约 95% 的观测不超过该值，既不代表最坏情况，也无法由少量请求稳定估计。

## 1．数值类型与决策边界

| 类型 | 典型例子 | 能否调节 | 正确问题 |
|---|---|---:|---|
| 数学或协议常量 | 余弦公式中的 `0.5`、交叉熵忽略标签 `-100`、INT8 范围 | 通常不能单独调 | 来源是什么？与哪些实现必须保持一致？ |
| 数据固有值 | 类别数、RGB 的 `3` 个通道、词表大小、样本数 | 由数据契约决定 | 换数据后哪些形状和制品必须同步？ |
| 实验缩放值 | 极小 hidden size、少量 step、小图片 | 可以调整，但主要控制实验成本 | 验证机制所需的最小规模，以及扩大规模后的适用边界。 |
| 模型结构参数 | 层数、宽度、Attention Head、FFN 比例、上下文长度 | 可以设计，但通常不能在加载权重后随意改 | 容量、显存、吞吐与质量的联动关系，以及整除或制品约束。 |
| 训练、推理与系统超参数 | 学习率、batch、warmup、temperature、并发、超时 | 需要通过实验或压测选择 | 优化目标是什么？依据哪些指标调？适用范围是什么？ |
| 随机种子 | 非 CV 默认 `42`；CV 默认 `3407` | 用于控制实验，不应按最好结果挑选 | 哪些随机源被控制？是否做了多种子确认？ |

“默认值”只表示库在调用者不传参数时采用的行为，不表示它是当前任务的最优值；“常见值”也只能作为实验起点。

## 2．随机种子：非 CV 用 42，CV 用 3407

随机种子把伪随机数生成器放到一个可重放的初始状态。它会间接影响参数初始化、数据打乱、Dropout、数据增强、采样和生成，但不改变学习算法本身。

| 种子 | 使用背景 | 解释边界 |
|---|---|---|
| `42` | 本课程所有非 CV 章节的单次实验、数据划分、采样与 Bootstrap 默认值 | 仅作为统一配置的普通整数，不具有更快收敛或更高质量的性质 |
| `3407` | 本课程只在 `E40_cv_vit.ipynb` 与 `E50_cv_diffusion.ipynb` 使用；该数值因 2021 年预印本《Torch.manual_seed(3407) is all you need》而知名 | 只是 CV 章节的统一标识；论文说明选择性报告有利种子会误导单次实验，并未证明 3407 更优 |

本课程约定：**CV 章节默认使用 `3407`，其余章节默认使用 `42`**。年份 `2026` 仅用于日期、快照或版本标识，不作为默认随机种子。模型评估中的多 Seed 实验应使用多个预先登记且互不相同的取值以估计波动；重复使用同一数值无法形成多 Seed 证据，这些取值也不代表各章的默认 Seed。

种子的正确使用方式：

1. 调试和机制验证阶段固定一个种子，使输入、初始化和采样更易重放。
2. 比较两个方案时，预先确定同一组种子和同一数据划分，不按结果为不同方案选择各自有利的种子。
3. 得出质量结论时运行多个种子，至少报告均值和离散程度；计算预算允许时再报告区间、最小值和最大值。
4. 数据划分、模型初始化、训练采样和推理解码最好使用分别命名的 seed，避免一个改动意外改变所有随机序列。
5. 保存 seed、数据版本、代码版本、关键文件哈希、框架版本、硬件和确定性设置。相同 seed 不保证跨 PyTorch 版本、平台、CPU/GPU 或不同 Kernel 得到逐 bit 相同的结果。

因此，seed 是**实验控制条件**，而不是通过搜索提高最终分数的质量超参数。更换 seed 的目的在于估计方差，不在于选择结果最有利的随机序列。参见 [PyTorch 可复现性说明](https://docs.pytorch.org/docs/stable/notes/randomness) 和 [3407 论文](https://arxiv.org/abs/2109.08203)。

Seed 无需满足质数、奇数、位数或数值大小等附加条件，只需位于目标框架接受的整数范围内。关键在于为不同随机源清晰命名、保存取值，并确保被比较方案采用相同的实验协议。

## 3．一套可复用的选择流程

超参数选择可按以下顺序进行，避免直接照搬脱离当前任务与资源条件的公开参数组合：

1. **先写目标和硬约束**：主指标、不能退化的安全指标、显存、吞吐、延迟、训练时长和成本。
2. **确认训练制度**：从头训练、全参数微调、LoRA、偏好优化和推理服务所适用的量级不同，不能混用参数表。
3. **建立可复现基线**：固定数据版本、评测集、模型 ID 与关键文件哈希、随机性范围和资源测量方法。
4. **先调最敏感参数**：通常先确定有效 Token Batch 和序列长度，再用对数尺度探索学习率，然后处理 warmup、正则和结构容量。
5. **综合评估证据**：同时分析训练/验证损失、目标质量、梯度范数、吞吐、峰值显存和失败样本，单次训练的最终 loss 不足以支持方案选择。
6. **多种子复核**：只在验证集上选择配置，用相同的预先登记种子复核；测试集在方案冻结后使用。
7. **冻结并记录适用域**：把最终配置、搜索空间、选择依据、硬件和验收结果写进制品 Manifest；数据、模型、batch、上下文或硬件变化后重新验证。

超参数通常对乘法变化更敏感，所以学习率、weight decay 等优先用对数尺度做粗搜索；接近稳定区域后再细化。一次只改一个参数只适合建立直觉，正式选择要考虑参数耦合。

## 4．训练超参数

### 4.1．优化与稳定性

| 参数 | 控制对象 | 选择依据 | 调整影响 | 联动复核项 |
|---|---|---|---|---|
| `learning_rate` / 峰值学习率 | 每次参数更新的步幅，是最敏感的训练参数之一 | 先按训练制度选起始量级，再做短程学习率扫描或对数搜索；全参数微调通常比 LoRA 更保守，因为被更新的预训练权重更多 | 过大常见 loss 激增、NaN 或能力遗忘；过小表现为下降缓慢、预算内欠拟合 | 有效 Token Batch、优化器、warmup、模型规模、精度、LoRA rank |
| optimizer | 如何利用梯度与历史动量更新参数 | AdamW 是 Transformer 常见基线；内存受限时可评估低精度优化器，但必须做质量与恢复测试 | 不同优化器会改变稳定区间、状态内存和吞吐 | 学习率、betas、epsilon、weight decay、checkpoint 格式 |
| Adam `beta1/beta2` | 一阶和二阶梯度统计的平滑程度 | 优先服从经验证的训练配方；只有出现响应迟钝、方差过大或缩放制度变化时再调 | 越接近 `1` 越平滑但响应更慢；更小则更快响应、噪声也更大 | 学习率、batch、梯度裁剪、混合精度 |
| optimizer `epsilon` | 防止除零并控制极小二阶矩下的数值行为 | 通常保持框架或模型配方值；低精度训练出现数值问题时才有证据地调整 | 过大可能改变有效步幅，过小可能失去数值保护 | dtype、loss scaling、归一化 epsilon；它们不是同一个参数 |
| `weight_decay` | 抑制权重过度增长的正则项 | 从模型配方起步，通过验证集选择；Bias 和归一化参数是否衰减要与优化器分组一致 | 过大导致欠拟合，过小可能过拟合或权重尺度失控 | 学习率、训练时长、数据量、参数分组 |
| `max_grad_norm` | 梯度裁剪阈值 | 用未裁剪梯度范数分布和异常 spike 决定，不把裁剪当成掩盖发散的手段 | 太低会长期压缩有效更新，太高则无法阻止异常更新 | 学习率、loss scaling、梯度累积、日志中的裁剪比例 |
| `dropout` | 训练时随机屏蔽激活以正则化 | 小数据或易过拟合任务从非零起点验证；确定性机制对齐时可以关闭 | 增大通常增强正则但减慢拟合；过大造成欠拟合 | 数据规模、模型容量、训练轮数；评估时必须关闭 |
| label smoothing | 把硬标签软化，降低过度置信 | 只有分类校准或泛化证据支持时启用；语言模型中还要确认 Padding/Mask 语义 | 增大可能改善校准，也可能削弱精确目标学习 | loss 定义、`ignore_index`、评测指标 |

学习率必须结合参数更新范围解释。同一数值用于随机初始化的小型模型、全参数微调和 LoRA 时具有不同含义。原理实验中的较大学习率用于在有限更新预算内形成可观察变化，不构成生产配置建议。

### 4.2．Batch、Token 与训练时长

| 参数 | 控制对象 | 选择依据 | 调整影响 | 联动复核项 |
|---|---|---|---|---|
| `per_device_batch_size` / micro-batch | 单设备一次前后向处理的样本数 | 先在目标序列长度下用显存实测找到稳定余量，不把显存占满作为唯一目标 | 增大可提高设备利用率，也会增加激活显存；样本长度不齐时“样本数”不能代表 Token 量 | 序列长度、packing、精度、activation checkpointing |
| `gradient_accumulation_steps` | 多少次 micro-batch 后做一次 optimizer update | 用于在显存不变时扩大有效 batch；按有效 Token 而非仅样本条数核算 | 增大减少更新频率、延长一次更新的墙钟时间，也会影响调度器步数解释 | 设备数、micro-batch、Token 数、loss reduction、梯度同步 |
| global/effective batch | 一次更新汇总的全局样本或 Token 数 | 对变长文本优先记录“每次更新的非 Padding Token” | 太大可能降低梯度噪声但减少同等 Token 预算下的更新次数；太小吞吐低且方差大 | 学习率、scheduler、数据 shuffle、分布式 world size |
| `max_seq_length` / context | 单样本可保留的最大 Token 数 | 从真实长度分布、截断损失、目标模型上限和显存共同选择 | 增大保留更多上下文，但普通 Attention 训练成本增长很快；过小会截掉答案或证据 | tokenizer、packing、位置编码、KV Cache、图像/视频 Token |
| `num_train_epochs` | 完整遍历训练集的次数 | 适合有限、稳定的数据集；用验证曲线与过拟合情况停止 | 增大提高数据复用，也提高过拟合和灾难性遗忘风险 | 数据量、学习率、数据重复率、early stopping |
| `max_steps` | optimizer update 的硬上限 | 适合流式或固定计算预算训练；必须明确 step 是 micro-step 还是 update step | 正值常会覆盖 epoch 预算；过小只验证链路，不能证明质量收敛 | 梯度累积、world size、scheduler、保存和评估间隔 |
| `logging/eval/save_steps` | 日志、评估和保存频率 | 根据一次 update 成本、故障恢复窗口和验证集成本选择 | 太密拖慢训练并制造大量制品；太疏则难以及时发现发散或恢复 | max steps、SLO、checkpoint 大小、保留策略 |
| early stopping patience | 指标多久不改善后停止 | 由评估噪声和评估间隔决定，不能只看一次抖动 | 太短会提前结束，太长会浪费预算并增加过拟合 | metric direction、最小改善量、eval frequency |

在 Hugging Face `TrainingArguments` 中，正数 `max_steps` 会覆盖 `num_train_epochs`。两者同时出现时必须在本章明确谁生效，不能让读者误以为两个条件都会执行。参见 [Trainer 参数文档](https://huggingface.co/docs/transformers/main_classes/trainer)。

若每个数据并行设备一次处理 `B_micro` 个样本、累积 `G` 次梯度、数据并行设备数为 `D`，则每次更新的全局样本数为 $B_{global}=B_{micro}\times G\times D$。对变长文本，更有意义的口径是所有设备和累积步中实际参与 Loss 的非 Padding Token 总数；相同样本 Batch 在长度分布变化后并不代表相同优化条件。

### 4.3．学习率日程、精度和内存

| 参数 | 控制对象 | 选择依据 | 主要风险 |
|---|---|---|---|
| warmup steps / ratio | 从小学习率升到峰值所用的更新或 Token 比例 | 观察训练初期 loss、梯度范数和混合精度溢出；大 batch 或从头训练通常更需要平滑启动 | 太短易早期不稳，太长会浪费大量预算在低学习率区间 |
| scheduler | 峰值后的学习率衰减方式 | 训练预算固定时常用线性或余弦；持续训练和再训练需明确末端学习率与续训语义 | 更换 scheduler 会改变整个更新积分，不能只比较同名峰值学习率 |
| minimum learning rate | 衰减末端保留的学习率 | 由是否继续训练、是否需要末期细化和训练总长决定 | 过高难以稳定收敛，归零后直接续训可能产生不连续 |
| FP32 / BF16 / FP16 / FP8 | 参数、激活、梯度或优化器状态的数值格式 | 服从硬件支持和模型配方；BF16 动态范围通常比 FP16 更稳，低精度必须做溢出与质量验收 | dtype 不只是节省内存，还会改变 Kernel、吞吐和数值误差 |
| loss scaling | 放大低精度梯度以减少下溢 | 主要服务 FP16；优先动态缩放并记录 overflow | 固定过大易溢出，过小保护不足 |
| gradient checkpointing | 用重算换激活显存 | 当激活成为瓶颈且额外计算可接受时启用 | 降低显存但增加训练时间，且可能改变可用 Kernel 路径 |

## 5．模型结构与 PEFT 参数

### 5.1．模型结构

| 参数 | 决定什么 | 选择与联动 |
|---|---|---|
| hidden size | 每个 Token 的表示宽度 | 影响绝大多数矩阵参数和计算；必须满足 Attention Head、并行切分和已加载权重的形状契约 |
| layers | 网络深度 | 增加顺序计算、激活和参数；与宽度一起在质量、吞吐和显存之间选择 |
| attention heads / KV heads | 查询并行子空间以及 KV Cache 结构 | hidden size 通常要能被 query head 数整除；GQA/MQA 的 KV Head 还直接影响缓存容量与 Kernel 支持 |
| FFN expansion / intermediate size | 每层 MLP 容量 | 经典比例只是架构起点；现代 gated FFN 和 MoE 的参数口径不同，必须读取精确 config |
| vocabulary size | Embedding 和输出头大小 | 由 tokenizer 制品决定；改词表需要同步映射、权重 resize 和兼容性验证 |
| context length | 位置范围和单请求 Token 预算上限 | 配置支持、训练覆盖、位置外推和服务能否承载是四件不同的事；标称上限不等于低成本或等质量 |
| experts / top-k | MoE 总专家数和每 Token 激活专家数 | active parameters 影响每 Token 计算，但总权重仍影响存储与显存；还要校验负载均衡和专家并行 |

结构参数不是在已有 checkpoint 上随意改动的旋钮。使用预训练模型时，首先读取模型仓库当前提供的 Config；只有训练新模型或有明确的结构迁移方案时才重新设计。

### 5.2．LoRA 与其他 PEFT

| 参数 | 控制对象 | 选择依据 | 调整影响 |
|---|---|---|---|
| `r` / rank | 低秩增量的容量 | 从较小 rank 建立基线；任务复杂、目标模块多样且验证仍欠拟合时再增加 | 增大可训练参数、优化器状态和 Adapter 大小，但不保证线性提升 |
| `lora_alpha` | LoRA 分支的缩放 | 必须结合实现中的缩放公式解释，重点看 `alpha/r` 或所用变体，而不是孤立看 alpha | 改变增量分支相对基座的幅度，会与学习率耦合 |
| `lora_dropout` | LoRA 分支的正则 | 小数据或过拟合时验证非零值；机制对齐可先设为零 | 增大可能改善泛化，也会减慢拟合；只在训练时生效 |
| `target_modules` | 哪些线性层可学习增量 | 根据架构名称、任务和可训练参数预算选择；Q/V-only 仅作为原理实现或历史起点 | 覆盖更多模块提高容量和显存，也提高制品对基座结构的耦合 |
| bias / modules to save | 除 LoRA 外还训练和保存什么 | 默认最小化可训练面；分类头、Embedding 等确需适配时显式加入 | 会改变可训练参数、保存内容以及合并/加载契约 |

LoRA 常允许比全参数微调更高的学习率，因为只更新低秩增量；这仍只是制度层面的起点，最终要由验证集、梯度和多种子结果决定。参数定义以 [PEFT LoRA 文档](https://huggingface.co/docs/peft/package_reference/lora) 和精确版本为准。

## 6．后训练与推理模型参数

| 参数 | 控制对象 | 选择依据与风险 |
|---|---|---|
| DPO `beta` | 偏好间隔相对参考策略约束的尺度 | 与 reward/log-prob 尺度和数据噪声共同校准；不能把某个库默认值当作所有任务的最优值 |
| KL coefficient | 策略偏离参考模型的惩罚 | 同时观察 reward、KL、熵和任务质量；过强学不到偏好，过弱可能策略漂移 |
| PPO/GRPO clip epsilon | 限制单次策略比率变化 | 结合 clipping fraction、KL 和训练稳定性选择；频繁被裁剪可能意味着更新过激 |
| group size / candidates | 同一问题的 Rollout 或候选数量 | 增大可改善相对比较或 Best-of-N 覆盖，但生成成本近似随候选数增加 |
| reward weights | 多个奖励信号的相对尺度 | 先分别归一化并做冲突分析；权重必须与业务约束和反作弊评测绑定 |
| reasoning token budget | 单次推理可用的思考或输出预算 | 按正确率—延迟—成本曲线选择；更长不保证更正确，还可能增加漂移和尾延迟 |

奖励、KL、熵和裁剪比例必须一起观察。只让 reward 上升并不能证明策略质量、安全性或泛化在改善。

## 7．数据、模型评估、RAG 与 Agent 参数

### 7.1．数据与模型评估

| 参数 | 控制对象 | 选择依据 | 常见误区 |
|---|---|---|---|
| train/validation/test 比例 | 分配给拟合、选择配置和最终估计的数据量 | 由总样本量、独立实体数、时间结构和所需置信度决定；用户、文档、会话或近重复应整体分组 | 把 `80/10/10` 或 `70/15/15` 当成标准答案；反复查看测试集调参 |
| split seed | 随机划分的可重放标识 | 一旦形成数据版本就冻结并写入 Manifest；正式实验还要覆盖其他合理划分或时间窗口 | 改训练 seed 时顺便改变测试成员，导致方案不可比 |
| truncation / filtering threshold | 哪些样本被截断、拒绝或清洗 | 先查看长度、质量或异常分布，再结合人工审计选择；记录被影响比例和样本 | 只看保留率，不检查被系统性丢弃的语言、群体或长尾 |
| classification threshold | 把分数转为业务决策的边界 | 在验证集上按误报/漏报成本、容量约束、PR/ROC 和校准情况选择 | 默认 `0.5` 只因输出像概率就直接使用；在测试集上反复挑阈值 |
| evaluation sample size | 指标包含多少独立案例 | 由目标误差范围、事件基率、切片数量和风险等级决定；同时报告样本数、点估计和不确定性 | 用几个样本算百分比或 P99；把 `0/n` 写成“绝对安全” |
| confidence level / bootstrap resamples | 区间覆盖口径与重采样近似精度 | 先按决策风险选覆盖率，再增加重采样直到区间端点稳定；同时固定重采样 Seed | 把 `95%` 当作模型有 95% 概率正确；只报告点估计 |
| metric averaging / weights | 多类别、切片或奖励的聚合方式 | 权重应对应业务暴露或明确政策，并同时保留逐切片指标 | 一个平均分掩盖高严重度或小群体失败 |
| Judge temperature / repetitions | LLM-as-a-Judge 的随机性与测量成本 | 确定性量表优先低随机；若生产评审有随机性则重复测量并报告一致性 | 把 Judge 当金标；不记录模型 ID、Rubric、位置顺序和解码配置 |
| regression tolerance / release threshold | 新版本相对冻结基线允许的变化 | 由业务最小有意义差异、置信区间、风险硬门禁与样本量共同确定 | 抄用别的项目百分比；在最终测试结果出来后移动门槛 |
| online traffic split / experiment duration | 在线实验暴露面与统计功效 | 先满足安全门禁，再根据基率、最小可检测效应、SLO 与可回滚性制定 | 用固定“5% 灰度”代替功效分析；只看互动率不看质量和伤害 |

评测本身也有生成 temperature、seed、候选数和最大输出长度。比较模型或策略时应冻结同一评测配置；若生产会采样，则评测也要覆盖多个预先声明的采样种子，而不是只测 Greedy 或只挑最好的一条生成。LLM-as-a-Judge 是需要校准的测量工具，不是无需人工金标的真值来源。

### 7.2．RAG 检索与上下文

| 参数 | 控制对象 | 选择依据 | 常见误区 |
|---|---|---|---|
| RAG chunk size | 单个索引单元包含多少结构或 Token | 按标题、段落、表格等语义边界建立候选，再用 Recall 和答案忠实度选择 | 用字符数跨语言照搬；块太小语义破碎、太大检索不精确 |
| chunk overlap | 相邻块重复多少上下文 | 用跨边界问题的召回增益对索引体积和重复证据成本做权衡 | overlap 越大越好；大量重复块会挤占上下文并放大重复引用 |
| retrieval `top_k` / score threshold | 进入上下文的候选数量和最低相关度 | 联合观察 Recall@K、噪声、上下文 Token 预算、无答案拒绝和引用覆盖 | K 增大只提升候选召回，不保证最终答案更好；不同检索器的分数阈值不能直接复用 |
| evidence token budget | System、Query、工具结果和输出预留之后可分给证据的 Token | 使用目标 Tokenizer 和 Chat Template 逐请求核算，并给格式和安全控制留余量 | 用字符数冒充 Token；把模型标称 Context 全部塞满 |

Embedding、稀疏/稠密混合、Reranker 与索引缓存是生产扩展，不是理解 RAG 的前置条件；只有单路检索在冻结集上无法满足召回或延迟目标时再引入，并重新建立基线。

### 7.3．Agent 执行预算

| 参数 | 控制对象 | 选择依据 | 常见误区 |
|---|---|---|---|
| max steps / tool calls | 单次任务允许的状态转换和外部动作数 | 从正常轨迹分位数、任务价值和循环风险反推，并区分平台硬上限与 Skill 预算 | 认为上限越大 Agent 越聪明；模型可以自行放宽预算 |
| total/input/output token budget | 问题、证据、工具结果与最终回答的总 Token 消耗 | 按上下文窗口、任务完成率和成本联合选择 | 只有 `max_new_tokens`，却不限制证据和工具结果增长 |

本课程用固定 Workflow 和最小 ReAct 风格循环解释 Agent：Workflow 的步骤由程序预定；ReAct 的每一 Turn 由一次 Decision 开始，非终止决策再产生一个 Action 和一个 Observation。`max turns`、步骤数和工具调用数都由程序计数，模型不能自行放宽；上限变大只表示允许更长循环，不表示能力更强。更复杂的运行治理不在本章展开。

## 8．生成与服务参数

### 8.1．文本生成

| 参数 | 控制对象 | 调整影响 | 选择依据 |
|---|---|---|---|
| `temperature` | 对 logits 除以温度后再采样，控制分布平坦度 | 高温更分散也更不稳定；低温更集中。`0` 在很多接口中表示改用 Greedy，而不是做除零 | 事实问答通常偏确定，创意任务可增加多样性；必须与采样开关和库语义一起记录 |
| `top_k` | 只保留概率最高的 K 个候选 | 小 K 更保守，大 K 接近不截断 | 根据任务错误成本和多样性评测选择 |
| `top_p` | 保留累计概率达到阈值的最小候选集合 | 小值更保守，大值保留更长尾部 | 与 temperature 联合调节，避免在缺少评测依据时叠加多个采样约束 |
| repetition penalty / frequency penalty | 抑制重复 Token 或模式 | 太强会破坏术语、代码和必要复述，太弱可能循环 | 在目标语言、代码和长文本集上评测 |
| `max_new_tokens` | 最多生成多少新 Token | 增大提高最坏延迟、成本和 KV Cache 占用；不会让模型自动利用全部预算 | 由答案长度分布、SLO、停止条件和配额决定 |
| stop sequences / EOS | 在何处结束生成 | 过宽会提前截断，缺失会产生多余尾部 | 必须绑定 tokenizer、Chat Template 和流式解析器 |
| generation seed | 复现随机采样路径 | 只影响启用采样时的随机路径，不提升答案质量 | 调试固定；质量评测覆盖多个采样种子 |

不同库对 `temperature=0`、`top_k=0`、是否启用 sampling 的语义可能不同，迁移时必须核对 [Transformers 生成文档](https://huggingface.co/docs/transformers/main_classes/text_generation) 和所用服务端版本。

### 8.2．服务与容量

| 参数 | 控制对象 | 选择依据 |
|---|---|---|
| batch / continuous batching | 每轮合并的请求量 | 用真实输入、输出长度和并发分布压测吞吐与尾延迟，不以平均请求代表生产流量 |
| concurrency | 同时在途请求数 | 受 KV Cache、调度器、外部依赖和 SLO 共同限制；过高会排队、OOM 或雪崩 |
| timeout / deadline | 单请求允许占用资源的最长时间 | 从端到端 SLO 反推各阶段预算；客户端、网关、模型和工具超时要形成单调收紧的预算链 |
| retries / backoff | 暂时故障后的重试次数与间隔 | 只重试幂等或可去重操作；加入抖动并受总 deadline 限制，防止重试风暴 |
| utilization target / memory margin | 为突发、碎片、滚动发布和故障保留余量 | 用峰值显存和队列分位数校准；追求接近满载通常会恶化尾延迟和恢复能力 |
| cache block/page size | KV Cache 分配粒度 | 小块减少内部浪费但增加元数据和调度开销；必须按后端 Kernel 与长度分布实测 |
| tensor/pipeline parallel size | 单副本跨多少设备 | 权重与 KV 能否放下只是底线，还要计算通信、并发副本数、故障域和成本 |

这些参数没有脱离工作负载的“推荐值”。章节中的吞吐、显存、超时和利用率都只是容量公式输入；上线前必须替换为目标模型、目标硬件和真实流量压测结果。

## 9．压缩、量化与多模态生成参数

### 9.1．压缩与量化

| 参数 | 控制对象 | 选择依据 |
|---|---|---|
| bit width | 权重或激活的表示精度 | 位宽越低通常越省内存，但质量取决于数据分布、量化粒度和目标 Kernel；“4-bit”不能单独说明格式与速度 |
| group size / per-channel | 多少元素共享量化 scale | 粒度越细通常误差更小，但元数据与 Kernel 复杂度更高 |
| calibration samples | PTQ 用哪些数据估计激活范围 | 覆盖真实生产分布比盲目增加数量更重要；通过误差/质量随样本增加是否稳定来决定规模 |
| sparsity / pruning threshold | 删除多少权重或结构 | 用质量门槛和真实稀疏 Kernel 吞吐共同选择；参数变少不自动等于运行更快 |
| distillation temperature / loss weights | 软化教师分布及平衡软、硬、特征目标 | 联合调节并验证任务质量与校准；公式中的 `T²` 是梯度尺度补偿，不是独立旋钮 |

### 9.2．图像、视频与扩散

| 参数 | 控制对象 | 选择依据 |
|---|---|---|
| image resolution / patch size | 图像细节和视觉 Token 数 | 分辨率增大、Patch 变小都会增加 Token；显存和 Attention 成本必须按二维面积重新计算 |
| frame count / FPS / duration | 视频时间覆盖和时间 Token 数 | FPS 控制采样密度，时长控制覆盖范围；不能把“更多帧”直接等同于“理解更好” |
| diffusion training timesteps | 训练时定义的噪声过程离散化 | 与 beta/sigma schedule 和预测目标绑定，属于训练配方，不能只改一个数字 |
| inference steps | 采样器调用模型的次数 | 更多步通常增加延迟且收益递减；必须对具体 scheduler、模型和质量指标评测 |
| guidance scale | 条件遵循相对无条件预测的强度 | 过高可能产生过饱和、伪影或多样性下降；模型蒸馏后适用范围也可能改变 |
| VAE scale / latent channels | 像素与 latent 的制品接口 | 必须从精确 VAE config 读取；不是跨 Stable Diffusion、FLUX 或视频模型通用的常数 |

## 10．数值配置的审查清单

评估关键数值时，可依次检查以下问题：

1. 控制对象、单位和作用范围分别是什么？
2. 它属于协议、数据契约、实验缩放、模型结构、可调超参数还是实验控制？
3. 本章为什么选这个值，依据是公式、上游制品、库默认、论文配方、资源预算还是短程实验？
4. 调大或调小会影响质量、稳定性、显存、吞吐、延迟和成本中的哪些方面？
5. 它和哪些参数存在整除、缩放、覆盖或资源耦合？
6. 哪些变化会使当前值失效，应该用什么指标重新选择？
7. 生产交付时需要记录哪些配置、版本和验收证据？

仅控制打印行数、图形尺寸或局部输出篇幅的数值无需附加解释，保留在相邻代码或图表配置中即可。只有当此类数值会改变算法语义、复现条件或验收结果时，才在对应代码或配置处说明其影响。
